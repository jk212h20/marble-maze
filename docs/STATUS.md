# Status: what is built, what is stubbed

A single place to answer "is this real yet?" for anything the game or the level format
mentions. It records *current state only*; the reason a rule exists belongs in
`DESIGN.md`, the level prose in `README.md`, and the order of work in `PLAN.md`.

The mechanic tables and the suite counts below are **generated** from
`src/engine/mechanics.js`, the built levels, and a real run of the suite, so they cannot drift
from the code. `node tools/gen-status.mjs --write` refreshes them;
`node tools/gen-status.mjs --check` fails if they are stale, and it also checks the totals
quoted in `README.md` and `PLAN.md`. CI runs the check.

the tuning sheet, the editor and the tests all handle it but no level does — so a player can

## Deliberately shelved

- Marble designs **bitcoin, geode, helix, gem, banded**: they build and still answer to
  `?marble=…`, but each costs a transmission pass per frame, so they are filtered out of the
  Look dial (`shelved: true` in `src/render/marbles.js`). Visible with `?all=1` in the lab.
- Slate levels **5–12**: concepts only (`src/engine/slate.js`), shown in the in-game
  *levels → Planned slate* menu so the progression can be discussed before it is authored.

## Known stale / unfinished paths

- `tools/level-editor/check.mjs` does **not** run the autopilot. Its own header says the
  solver "has not kept up with the engine (vials, slot pits, sub-unit placement, a growing
  obstacle vocabulary)", so a solved/not-solved verdict there would mislead. `--solve` only
  reports that. Solvability is checked by `tests/run.js` instead, and `PLAN.md` Phase 4 owns
  closing this.
- The autopilot proof covers single-marble levels. `both-locks` is `coop: true` and is proven
  by a scripted two-marble plan in `tests/lifts.test.js`.
- The fan's visible airstream is deferred on purpose: `DESIGN.md` calls it "later", and slate
  level 8 is not authored until the "readable tell" question is answered.

## Test coverage

`npm run check` is the gate: `npm test` (the node suite, no browser, no GPU) plus
`tools/check-levels.mjs`, which puts every shipped level through the level editor's own
validator, plus `tools/gen-status.mjs --check` for the numbers in this file.

**Not in that gate** (they need a browser, so they run as a second CI job):

- `node sim/render-parity.mjs` — every mechanic on the built board, and the flap measures as standing
  in the marble's way rather than floating above it.
- `node sim/smoke.mjs` — loads the real page, drives it, screenshots, times frames.
- `node sim/tune-check.mjs` — the panel changes the simulation; keys inside it do not tilt.
- `node sim/audio-check.mjs` — renders every voice offline and reports level/balance.
- `npm run check:browser` runs all three, starting the dev server on an ephemeral port.

**Deliberately not in CI** (they need a real GPU):

- `npm run perf` and `npm run marble-cost`.
- `npm run marbles`, `npm run marble-board`, `npm run materials`, `npm run panel`, `npm run rim`
  — lab and documentation shots, run by hand when a look changes.

**Gaps worth naming:**

1. **The renderer has no unit coverage.** `scene.js` is the largest file in the repo; CI
   reaches one pure function of it (`transmissionBufferScale`, in `tests/marbles.test.js`) and
   the rest is exercised only in the browser. `PLAN.md` Phase 3 owns this, and
   `tests/mechanics.test.js` is the first half of it: it proves every mechanic a level uses has
   *some* visual, not that the visual is right.
2. **Unbuilt-level mechanics are tested on fixtures.** `physics.test.js` builds a tiny
   synthetic level per feature; `levels.test.js` and `solver.test.js` iterate only the four
   authored levels. There is no end-to-end guard that a belt reads correctly on a real board.
3. **The browser and GPU layers are manual** apart from the three smoke checks, so a visual
   regression is caught when someone runs the shot tools, not before.
